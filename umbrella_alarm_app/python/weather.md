## 1단계
이 저장소는 UNO Q의 MCU(아두이노 스케치)에서 동작하는 "우산 알림 장치" 펌웨어다. 기능을 3단계로 나눠서 추가할 것이며, 이번이 1단계다. 이번 단계에서는 센서 감지와 상태 전송만 만들고, 음성 수신과 재생은 만들지 마라. 나중에 붙일 수 있게 자리만 남겨라.

## 전체 시스템 (참고용)
- 리눅스(MPU)가 아두이노가 보낸 센서 상태를 받아 세 조건(문이 닫힘→열림으로 바뀐 순간, 비 예보 있음, 우산 미지참)을 판단한다. 모두 충족하면 gTTS로 안내 문장을 MP3로 만들어 UART로 아두이노에 보낸다.
- 아두이노(MCU)가 맡는 일은 ① 문·우산 센서 감지 후 상태 전달, ② 음성 수신 준비(READY 응답), ③ MP3 수신(512바이트씩), ④ 재생 후 OK 응답이다. 알림 조건 판단은 아두이노가 하지 않는다.
- 이번 1단계 범위는 ①뿐이다.

## 하드웨어 가정 (확실하지 않은 것은 임의의 값으로 표시)
- FSR402: 3.3V - FSR - A0 - 10kΩ - GND 분압 회로, 눌릴수록 값이 커진다. ADC 10비트(0~1023), 로직 3.3V 가정.
- MC-38: 디지털 2번, INPUT_PULLUP, 문 닫힘일 때 LOW(NC 타입) 가정. 실제 극성은 확인 후 바꿀 수 있게 상수로 분리하고 주석으로 남겨라.

## 만들 것
1. 파일 구성 (스케치 폴더 안에 여러 파일로 나눠라)
   - 메인 .ino: setup(), loop()에서 단계 함수를 순서대로 호출만 한다.
   - config.h: 임의의 값 모음(아래 규칙 참고)
   - sensors.h/.cpp: FSR 평균 읽기, MC-38 디바운스, 우산 유무와 문 상태 확정
   - link.h/.cpp: 리눅스와의 통신 계층. 줄 단위 문자열 송수신 함수(linkSendLine, linkReadLine)를 한 곳에 모아라. 지금은 Serial을 쓰되, UNO Q에서 MCU와 리눅스가 실제로 어떤 API(Serial, Bridge 등)로 통신하는지 공식 문서에서 확인해라. 확실하지 않으면 추측하지 말고 Serial로 두고 `// TODO: 통신 방식 확인 필요`로 남겨라.
2. 센서 상태 확정
   - 우산: FSR 평균(최근 5개)이 ON 기준 이상이면 "있음", OFF 기준 이하면 "없음", 사이에서는 이전 상태 유지(히스테리시스).
   - 문: MC-38 값이 디바운스 시간 동안 유지될 때만 상태 변경.
   - 상태는 SystemState 구조체 하나에 모아서 전달하고, 전역 변수를 흩뿌리지 마라.
3. 상태 전송
   - 상태가 바뀐 순간 즉시 한 줄 전송하고, 변화가 없어도 일정 주기마다 한 줄씩 보낸다(리눅스가 이전 문 상태와 비교해 전환을 감지하기 때문).
   - 형식: `STATE,<time_ms>,<fsr>,<door_open>,<umbrella_present>` (door_open과 umbrella_present는 0 또는 1, 줄 끝은 \n)
4. 통신 규약 문서 PROTOCOL.md 작성 (아래 규약을 그대로 문서화)
   - 아두이노 → 리눅스 (텍스트 한 줄): `STATE,...` / `READY` / `OK` / `ERR,<코드>`
   - 리눅스 → 아두이노: `AUDIO,<byte_size>` 한 줄. 이후 READY를 받으면 byte_size만큼의 바이너리 데이터를 512바이트씩 전송한다. 데이터 수신이 끝나면 다시 텍스트 한 줄 모드로 돌아온다.
   - ERR 코드: `TIMEOUT`, `SIZE`, `PLAY` (2, 3단계에서 사용)
   - 이번 단계에서는 STATE만 구현하고, 나머지는 문서에만 적는다.
5. CLAUDE.md 작성: 아래 코딩 규칙을 그대로 적어서 이후 단계에서도 이 규칙을 따르게 해라.

## 코딩 규칙 (CLAUDE.md에도 적을 것)
- delay()를 쓰지 말고 millis() 기반으로 주기를 처리한다(블로킹 금지).
- 임의로 정한 값은 모두 config.h에 const로 모으고, 각 줄에 `// 임의의 값:` 으로 시작하는 한국어 주석을 단다. 주석에는 "이 값이 무엇을 의미하는지"와 "나중에 무엇으로 바꿔야 하는지"를 적는다.
  - 예: `const int FSR_ON_THRESHOLD = 300;  // 임의의 값: 우산 있음으로 판정하는 FSR 기준값. 9주차 반복 측정 후 실측값으로 교체`
- 임의의 값 목록: FSR 핀(A0 가정), MC-38 핀(2번 가정), FSR 읽기 주기 50ms, MC-38 읽기 주기 20ms, FSR 평균 개수 5, 우산 있음 기준 300 이상 / 없음 기준 250 이하, MC-38 디바운스 30ms, 상태 전송 주기(변화 없을 때) 500ms, 통신 속도 115200, MC-38 문 닫힘 시 LOW 여부
- 함수마다 한 줄 설명 주석(한국어)을 단다.
- 확실하지 않은 보드 사양이나 API는 추측하지 말고 TODO로 남기거나 사용자에게 물어라.

## 1. 바뀐 통신 규약 (이전 규약은 폐기)
- 폐기: `AUDIO,<byte_size>` 줄, MP3 수신, "재생 완료 후 OK"
- 새 흐름
  - 리눅스는 알림 조건 충족 시 gTTS로 MP3를 만들고 FFmpeg로 PCM(8,000Hz, unsigned 8비트, 모노)으로 변환한다.
  - 아두이노가 먼저 `READY\n`을 보낸다. 리눅스는 READY를 받은 뒤 PCM 헤더 13바이트 + 본문을 최대 512바이트씩 보낸다.
  - 아두이노는 본문을 모두 받으면 `OK\n`을 보낸다. OK는 "수신 완료"이고 "재생 완료"가 아니다. 재생은 OK 이후에 시작한다.
- 리눅스 → 아두이노 방향에는 이제 텍스트 줄이 없고 바이너리 PCM 패킷만 있다. 1단계에서 이 방향의 줄 단위 명령 처리를 만들었다면 제거하거나 PCM 수신 시작 판단으로 바꿔라.
- 아두이노 → 리눅스 방향의 텍스트 줄: `STATE,...`(1단계 형식 그대로 유지), `READY`, `OK`, 선택적으로 `ERR,<코드>`, `DBG,<메시지>`

## 2. 정리 작업
- PROTOCOL.md를 위 새 규약으로 전면 갱신해라. 폐기된 규약은 "폐기" 표시와 함께 맨 아래에 남기지 말고 삭제해라.
- link 모듈에 바이트 단위 읽기 함수(예: linkAvailable, linkReadByte 또는 linkReadBytes)를 추가해라. 기존 줄 송신 함수(linkSendLine)와 센서 상태 전송은 그대로 동작해야 한다.
- 1단계의 센서 감지, SystemState 구조체, STATE 전송 형식과 시뮬레이션 기능(SIMULATE_SENSORS)은 바꾸지 마라. 1단계 시험이 여전히 통과해야 한다.
- 수정 후 1단계 동작(STATE 줄 출력)이 깨지지 않았는지 확인해라.

## 3. 새로 만들 것: audio_rx.h/.cpp (상태: IDLE → RECEIVING → RECEIVED)
- READY 전송 규칙: IDLE일 때만 `READY\n`을 보낸다. 수신 중이거나 재생 중에는 보내지 않는다. 전송 시점은 ① 부팅 직후 1회 ② 수신 또는 재생이 끝나 IDLE로 돌아온 직후 1회 ③ IDLE이 계속되는 동안 READY_REPEAT_MS 주기로 반복. 반복 전송은 READY_REPEAT_ENABLED 상수로 끌 수 있게 해라.
- IDLE에서 들어온 바이트가 헤더 매직과 일치하면 헤더 수신을 시작한다. 일치하지 않는 바이트는 버린다.
- 헤더 13바이트 파싱은 parsePcmHeader() 한 함수에만 모아라. 실제 구조는 리눅스 담당에게 확인 중이므로, 확정 전까지 아래 구조를 가정하고 `// 임의의 값: 실제 헤더 구조 확정 후 교체`로 표시해라.
  - 매직 "PCM" 3바이트 + 샘플레이트 4바이트(리틀 엔디언) + 비트 수 1바이트 + 채널 수 1바이트 + 본문 길이 4바이트(리틀 엔디언) = 13바이트
- 헤더 검증: 샘플레이트 8000, 비트 수 8, 채널 1이 아니거나 본문 길이가 0이거나 AUDIO_MAX_BYTES를 넘으면 수신하지 않고 IDLE로 돌아간다(ERR_REPORT_ENABLED가 true이면 `ERR,HEADER` 또는 `ERR,SIZE` 한 줄도 보낸다).
- 본문은 헤더의 길이만큼 512바이트(CHUNK_SIZE) 단위로 읽는다. 마지막 청크는 남은 바이트만 받는다.
- 청크 사이 대기 시간이 AUDIO_CHUNK_TIMEOUT_MS를 넘으면 수신을 중단하고, 남은 입력 바이트를 비운 뒤 IDLE로 돌아간다(ERR_REPORT_ENABLED이면 `ERR,TIMEOUT`).
- 본문을 길이만큼 모두 받으면 `OK\n`을 보내고 RECEIVED 상태가 된다. `audioRxIsComplete()`, `audioRxGetData()`, `audioRxGetSize()`로 3단계에서 가져갈 수 있게 하고, 재생은 하지 마라.
- loop()가 블로킹되지 않게, 읽을 수 있는 만큼만 읽고 돌아오는 구조로 만들어라.

## 4. 메모리
- PCM은 초당 8,000바이트다. 버퍼 크기 = 8,000 × AUDIO_MAX_SECONDS. 이 MCU의 사용 가능한 RAM을 공식 문서에서 확인해서 버퍼가 들어가는지 판단해라. 수치를 확실히 모르면 추측하지 말고 "확인 필요"로 적어서 나에게 알려라. 버퍼는 AudioBuffer 추상화 뒤에 두어라.

## 5. 센서 전송과의 관계
- 수신 중에는 STATE 전송을 멈추고, 수신이 끝나거나 실패하면 즉시 STATE를 한 줄 보낸다.
- 같은 시리얼 선을 쓰는 경우를 고려해서, 디버그 출력은 모두 `DBG,` 접두사를 붙이고 DEBUG_PRINT(임의의 값: 기본 false)로 끌 수 있게 해라.

## 6. 시험용 스크립트 tools/send_pcm_test.py (pyserial 사용)
- 포트와 속도를 인자로 받는다. 시리얼을 열고 READY를 기다린 뒤, 13바이트 헤더 + 본문을 512바이트씩 보내고 OK를 기다린다. 중간에 오는 STATE 줄은 무시한다.
- 본문은 PCM 파일 경로를 인자로 받거나, 인자가 없으면 440Hz 사인파(8,000Hz, unsigned 8비트, 모노, 1초)를 직접 만들어 보낸다.
- README에 MP3를 PCM으로 바꾸는 방법을 적어라: `ffmpeg -i in.mp3 -ar 8000 -ac 1 -f u8 out.pcm`

## 만들 것
1. audio_player.h/.cpp: 재생 인터페이스와 구현 2종
   - 인터페이스: begin(), start(data, size), update()(매 loop 호출, 블로킹 금지), isPlaying(), stop()
   - AUDIO_OUTPUT_MODE 상수(임의의 값: 기본 BUZZER)로 구현을 고른다.
     - BUZZER 모드: 부품 목록에 "부저 모듈로 대체"가 적혀 있으므로, 수신한 데이터를 재생하는 대신 정해진 비프 패턴(길이와 횟수는 임의의 값)을 millis() 기반으로 울린다. 재생을 시작한 순간부터 패턴이 끝날 때까지를 "재생 중"으로 본다.
     - MP3 모드: 실제 MP3 재생. 이 MCU와 디지털 앰프 모듈로 MP3를 디코딩해서 출력하는 방법(디코더 라이브러리, I2S 등)은 공식 문서와 사용 중인 앰프 모듈 사양서를 확인해라. 확실하지 않으면 추측해서 코드를 쓰지 말고, 가능한 방법 2~3가지와 각각 필요한 부품을 정리해서 나에게 알려라. 이 경우 MP3 모드는 스텁(재생 시간을 `크기 / 임의의 값(바이트/초)`로 흉내 내서 대기)으로 두고 `// TODO: 실제 디코더 연결`로 표시해라.
2. 전체 상태 전환 통합 (메인 .ino)
   - 상태: SENSING → RECEIVING → PLAYING → SENSING
   - SENSING: 센서 읽기와 STATE 전송. `AUDIO,<n>` 줄을 받으면 RECEIVING으로 전환.
   - RECEIVING: 2단계의 수신 모듈 동작. 완료 시 PLAYING으로, 실패(ERR) 시 SENSING으로 복귀.
   - PLAYING: audio_player를 시작하고 update()로 진행. 재생이 끝나면 `OK`를 한 줄 보내고 SENSING으로 복귀한 뒤 즉시 STATE를 한 줄 보낸다.
   - 재생 시간이 PLAY_TIMEOUT_MS(임의의 값)를 넘으면 `ERR,PLAY`를 보내고 재생을 중단한 뒤 SENSING으로 복귀한다.
   - 어떤 상태에서든 loop()가 블로킹되지 않아야 한다.
3. 상태 전환 코드를 한 함수(예: runStateMachine())로 모아서 메인 .ino의 loop()는 그 함수와 센서 읽기만 호출하게 정리해라.
4. 정리와 문서
   - PROTOCOL.md에 전체 흐름(STATE → AUDIO → READY → 데이터 → OK)과 ERR 코드를 최신 내용으로 갱신해라.
   - README.md에 구성 파일, 임의의 값 목록과 교체 시점(9주차 측정 후, 부품 확정 후 등), 시험 방법을 정리해라.
   - tools/send_audio_test.py가 OK 응답까지 확인하도록 갱신해라.

## 시험 시나리오 (README에 정리)
- 정상: STATE 전송 → `AUDIO` 전송 → READY → 데이터 → 재생 → OK → STATE 재개
- 수신 실패(ERR,TIMEOUT 또는 ERR,SIZE) 후 센서 감지 복귀
- 재생 중 타임아웃(ERR,PLAY) 후 복귀
- 재생 직후 문 상태가 바뀌어 있어도 첫 STATE가 현재 상태를 정확히 보내는지

컴파일 확인이 가능하면 해라.
